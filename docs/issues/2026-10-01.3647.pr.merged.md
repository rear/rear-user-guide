# [\#3647 PR](https://github.com/rear/rear/pull/3647) `merged`: Skip unsupported mkfs.xfs -i sparse= on older xfsprogs

**Labels**: `enhancement`, `bug`, `fixed / solved / done`

#### <img src="https://avatars.githubusercontent.com/u/61417309?v=4" width="50">[sebastian-koehler](https://github.com/sebastian-koehler) opened issue at [2026-10-01 17:19](https://github.com/rear/rear/pull/3647):

-   Type: **Bug Fix**

-   Impact: **High** — `rear recover` currently fails to (re)create the
    root filesystem at all on any target whose `mkfs.xfs` predates
    `-i sparse=` support (e.g. RHEL 7.9 / xfsprogs 4.5.0), and the
    failure isn't a clean abort: the disk-layout-recreation menu just
    keeps re-running the same failing command forever, which looks like
    a hang rather than an error.

-   Reference to related issue (URL): None filed — found during live
    end-to-end NBU recovery testing, not tracked as a separate issue.

-   How was this pull request tested?

    Reproduced on a real RHEL 7.9 NetBackup client
    (`xfsprogs`/`mkfs.xfs` 4.5.0). `rear recover` consistently failed at
    the disk-layout-recreation step with:

        mkfs.xfs -f -m uuid=... -i sparse=0 ... /dev/mapper/rhel-root
        unknown option -i sparse=0

    Confirmed via the captured `rear recover` log and `lsblk`/xfs\_info
    output that `xfs_info` on this xfsprogs version already reports a
    `spinodes` attribute, but the paired `mkfs.xfs` binary doesn't
    accept `-i sparse=` at filesystem-creation time — so `xfs_parse()`
    was generating an option the local `mkfs.xfs` can't handle.
    Validated the fix with `bash -n`, then deployed it into the live
    booted rescue environment on the same RHEL 7.9 host for a
    `rear recover` retest.

-   Description of the changes in this pull request:

    Adds `mkfs_xfs_supports_sparse_inodes()` to
    `usr/share/rear/lib/filesystems-functions.sh`, which probes the
    target's own `mkfs.xfs` usage output (run without a device argument)
    to check whether it actually supports the `-i sparse=` suboption,
    rather than assuming a fixed xfsprogs version cutoff. `xfs_parse()`
    now skips emitting `-i sparse=...` when the probe says it's
    unsupported, so filesystem recreation falls back to `mkfs.xfs`
    defaults for that option instead of failing outright.

    The probe matches on a word boundary (`grep -qw 'sparse'`) rather
    than a plain substring, so it only fires on the literal `sparse`
    suboption in `mkfs.xfs`'s usage output and can't false-positive on
    some other option name that merely contains "sparse" as a substring.

#### <img src="https://avatars.githubusercontent.com/u/29474856?u=b3637dbf6b72d36a96742d81028e6361add0d388&v=4" width="50">[svlv](https://github.com/svlv) commented at [2026-10-02 07:15](https://github.com/rear/rear/pull/3647#issuecomment-5947224916):

The `sparse` option is hanled in `filesystems-functions.sh`. It was
added by me:

    # xfs_info v4.5.0 on RHEL 7 reports 'spinodes' instead of 'sparse'
    xfs_param_iname[18]="spinodes"
    xfs_param_search[18]="metadata_section"
    xfs_param_opt[18]="-i"
    xfs_param_name[18]="sparse"

Since we are using a custom rescue system with an updated version of
`xfs-progs`, the issue was not encountered.

However, `mkfs.xfs` on RHEL 7 indeed does not support the
`-i sparse=0|1` option, which leads to errors during filesystem
recreation.

The problem is that `xfs_info` reports the sparse feature differently:
as `spinodes` (a contraction of sparse inodes) on RHEL7, and as `sparse`
since RHEL8, I believe.

Please compare the output of `xfs_info` on RHEL7 and RHEL10:

    [root@rhel7 ~]# xfs_info /dev/mapper/rhel-root
    meta-data=/dev/mapper/rhel-root  isize=512    agcount=4, agsize=1113856 blks
             =                       sectsz=512   attr=2, projid32bit=1
             =                       crc=1        finobt=0 spinodes=0 <===
    data     =                       bsize=4096   blocks=4455424, imaxpct=25
             =                       sunit=0      swidth=0 blks
    naming   =version 2              bsize=4096   ascii-ci=0 ftype=1
    log      =internal               bsize=4096   blocks=16384, version=2
             =                       sectsz=512   sunit=0 blks, lazy-count=1
    realtime =none                   extsz=4096   blocks=0, rtextents=0

    root@rhel10:~# xfs_info /dev/mapper/rhel-root
    meta-data=/dev/mapper/rhel-root  isize=512    agcount=4, agsize=1665280 blks
             =                       sectsz=512   attr=2, projid32bit=1
             =                       crc=1        finobt=1, sparse=1, rmapbt=1 <===
             =                       reflink=1    bigtime=1 inobtcount=1 nrext64=1
             =                       exchange=0
    data     =                       bsize=4096   blocks=6661120, imaxpct=25
             =                       sunit=0      swidth=0 blks
    naming   =version 2              bsize=4096   ascii-ci=0, ftype=1, parent=0
    log      =internal log           bsize=4096   blocks=16384, version=2
             =                       sectsz=512   sunit=0 blks, lazy-count=1
    realtime =none                   extsz=4096   blocks=0, rtextents=0

Since mkfs.xfs uses `sparse=0|1`, I added the corresponding mapping to
cover both `spinodes` and `sparse`.

By the way, the following information is provided in `man mkfs.xfs` on
RHEL 7:

    sparse[=value]
                              Enable sparse inode chunk allocation.
                              This experimental option is not available in RHEL7.
