Add SKIP\_UNSUPPORTED\_PARTITION\_TABLES (default yes) to skip
sun/unknown/loop disks before writing disk/part lines. Extends \#3455
EXCLUDE\_COMPONENTS handling with fleet-scale auto-skip. Adds 315 script
and 230 filesystem skip. Related: \#3455

-   How was this pull request tested?

Test 1 — default auto-skip (SKIP\_UNSUPPORTED\_PARTITION\_TABLES=y) :  
Ran rear mkrescue -v , succeeds without including sun disk in
disklayout.conf

Test 2 — strict mode (SKIP\_UNSUPPORTED\_PARTITION\_TABLES=n):  
mkrescue fails with clear Error on unsupported partition table

Test 3 — regression for \#3455 (EXCLUDE\_COMPONENTS):  
`SKIP_UNSUPPORTED_PARTITION_TABLES=n` +
`EXCLUDE_COMPONENTS+=( /dev/vdX )` on unsupported disk  
Then rear mkrescue -v , Disk in EXCLUDE\_COMPONENTS is skipped, honoring
exclusion added even if unsupported skip is set to No.

-   Description of the changes in this pull request:  
    Since ReaR 2.7+ ([\#2803](https://github.com/rear/rear/pull/2803)),
    layout/save/GNU/Linux/200\_partition\_layout.sh errors out when
    parted reports an unsupported partition table type (e.g. sun,
    unknown, loop, bsd). This causes mkrescue to abort on systems with
    legacy non-OS data disks that ReaR cannot recreate anyway.

[\#3455](https://github.com/rear/rear/pull/3455) added a soft-fail path
in extract\_partitions() when the disk is explicitly listed in
EXCLUDE\_COMPONENTS. That helps exceptional cases but does not scale for
large fleets where per-host EXCLUDE\_COMPONENTS configuration is
impractical. Furthermore, EXCLUDE\_COMPONENTS is processed in script
310\_include\_exclude.sh, which runs after 200\_partition\_layout.sh, so
unsupported disks without sysfs partition entries can still abort layout
save before exclude logic runs.

This pull request adds SKIP\_UNSUPPORTED\_PARTITION\_TABLES=y (default)
to skip unsupported disks during layout save:

usr/share/rear/conf/default.conf — new parameter
SKIP\_UNSUPPORTED\_PARTITION\_TABLES=y; set to n for strict Error
behavior.

usr/share/rear/lib/layout-functions.sh — new helper
is\_partition\_table\_type() for supported types (msdos, gpt,
gpt\_sync\_mbr, dasd).

usr/share/rear/layout/save/GNU/Linux/200\_partition\_layout.sh:

Initialize $VAR\_DIR/layout/skipped\_unsupported\_disks  
In the disk loop: detect disktype via parted (with 2&gt;/dev/null);
treat empty parse result as unknown; skip unsupported disks before
writing active disk lines when auto-skip is enabled  
In extract\_partitions(): keep \#3455 EXCLUDE\_COMPONENTS soft-fail; add
auto-skip via SKIP\_UNSUPPORTED\_PARTITION\_TABLES  
usr/share/rear/layout/save/GNU/Linux/230\_filesystem\_layout.sh — skip
saving filesystem layout for devices on skipped disks.

usr/share/rear/layout/save/default/315\_skip\_unsupported\_partition\_tables.sh
(new) — mark skipped disks, their filesystems, and swap as done so
330\_remove\_exclusions.sh comments them out in disklayout.conf.

Skipped disks are recorded as commented \# Skipped disk ... lines in
disklayout.conf for auditability. Supported OS disks (gpt/msdos/dasd)
are unchanged.

I think this is a too severe backward incompatible change  
in ReaR behaviour to skip unsupported partition table types  
by default.  
Assume an experienced ReaR user got a new system  
where also an unsupported partition table type exists.  
An experienced ReaR user knows that ReaR errors out  
in such cases.

Furthermore it is ReaR's default task to  
recreate a system "as it was before".  
So ReaR must not automatically skip things  
when ReaR does not support something but instead  
ReaR must error out when it cannot do its default task.

Therefore I think in default.conf there should be

    SKIP_UNSUPPORTED_PARTITION_TABLES=''

which should default to "no".

The crucial point is that it must be an explicit  
user request via a user specified setting like

    SKIP_UNSUPPORTED_PARTITION_TABLES="yes"

where the user commands ReaR to skip disks  
with unsupported partition table types.

Indeed. ReaR should fail early if it detects something that it will not
be able to recreate. Silently excluding stuff that it is not able to
handle and thus potentially losing data is IMO a very bad idea. The
administrator has to decide what to do in this case.

Before making a change to the default, I would like to review what is
actually the desired behavior here. According to private conversations,
the original problem is that PR \#2803 (more precisely, commit
825478ee27f916553938afaf5164fec22cb32732) introduced a regression. It
fixed the issue \#2801 where in the presence of unsupported partition
tables a broken layout got generated. But it fixed it by making ReaR
error out early. The problem is, this is a regression for users where
those disks got excluded using some `*EXCLUDE_*` / `*INCLUDE_*`
variable - the broken entries in the layout got excluded afterwards, so
this was not an issue unless the disk was being used or
`AUTOEXCLUDE_DISKS=n` was specified in the configuration.

I would therefore propose to fix the problem in a different way. We
should change ReaR so that the unsupported partition table causes an
error only if the partition are actually used. This would lead to the
same error as now for users that have configurations that can not be
restored properly, but ReaR would work as before out of the box for
users who do not have the problematic disks mounted or exclude them via
any of the `*EXCLUDE_*` / `*INCLUDE_*` parameters. We would not add any
new configuration option. (I feel that there are way too many
`*EXCLUDE_*` / `*INCLUDE_*` parameters already, and as the person who
has sometimes write docs about what they do, how they are used and how
they interact I would very much prefer to avoid adding any new ones
unless really needed.)

The reason is that ReaR cannot detect that ZFS is used  
because in layout/save/GNU/Linux/230\_filesystem\_layout.sh  
we do (excerpts)

    supported_filesystems="ext2,ext3,ext4,vfat,xfs,reiserfs,btrfs"
    ...
    read_filesystems_command="mount -t $supported_filesystems | cut -d ' ' -f 1,3,5,6"
    # If the findmnt command is available use it instead of the traditional mount command
    ...
    findmnt_command="$( type -P findmnt )"
    if test -x "$findmnt_command" ; then
        ...
        read_filesystems_command="$findmnt_command -mnrv -o SOURCE,TARGET,FSTYPE,OPTIONS -t $supported_filesystems"

so ReaR calls

    mount -t ext2,ext3,ext4,vfat,xfs,reiserfs,btrfs | cut -d ' ' -f 1,3,5,6

    findmnt -mnrv -o SOURCE,TARGET,FSTYPE,OPTIONS -t ext2,ext3,ext4,vfat,xfs,reiserfs,btrfs

and all the rest works based on that output  
which must not contain unsupported filesystems
