#### <img src="https://avatars.githubusercontent.com/u/48823770?v=4" width="50">[lzaoral](https://github.com/lzaoral) commented at [2026-08-05 15:05](https://github.com/rear/rear/pull/3622#issuecomment-5193509995):

@jsmeix First, I'd like to apologise that my previous reply was worded a
bit too strongly.

> I don't see why the GRUB configuration regarding  
> ReaR's special auto\_recover kernel option  
> depends on the OUTPUT method?

Right now, you have a couple of options that are only relevant for
specific output and bootloader combinations:

1.  `ISO_DEFAULT` and `ISO_RECOVER_MODE` are currently relevant only for
    `OUTPUT=ISO` and `ISOLINUX`.
    -   They are ignored when GRUB2 is used.
2.  `PXE_RECOVER_MODE` which is only relevant for `OUTPUT=PXE` and
    `PXELINUX`
    -   They are ignored when GRUB2 is used.
3.  `USB_BIOS_BOOT_DEFAULT` or `GRUB2_TIMEOUT` which are only relevant
    for `OUTPUT=USB` and `EXTLINUX`
    -   They are ignored when GRUB2 is used.
4.  `GRUB2_DEFAULT_BOOT` which is only relevant for GRUB2 on BIOS or EFI
    machines with `OUTPUT=ISO` and `OUTPUT=USB`.
    -   They are ignored when `OUTPUT=PXE` is used or when a different
        firmware is used, e.g. `OUTPUT=ISO` PowerVM.
5.  No options are applicable for `OUTPUT=PXE` with GRUB or `OUTPUT=ISO`
    on Power.

This PR somewhat improves the state but also introduces an inconsistent
and counterintuitive behaviour. Given the current reuse of the GRUB2
menu generation functions in the case 4 mentioned above for `OUTPUT=ISO`
and `OUTPUT=USB`, both `ISO_DEFAULT` and `ISO_RECOVER_MODE` would be
effective even when `OUTPUT` is set to `USB`.

My (longer-term) goal is to incrementally reach a state where we have
only a set of options that are applicable in all the cases above, e.g.
`BOOTLOADER_TIMEOUT`, `BOOTLOADER_DEFAULT_ENTRY`, ..., and to have the
older options deprecated. My plan is to have this work done before 3.0
is released since that will be a major release, thus, bigger/breaking
changes would be expected there.

Without detailed analysis I think the root cause  
why there are such inconsistencies is the same  
as for many other inconsistencies in ReaR:

Usually things move forward in ReaR not managed  
by some "grand master plan" but mostly "ad hoc"  
as needed and limited to solve specific issues  
and as far as possible by the contributors  
who implement something.

One cannot expect that a contributor  
who implements something to solve a specific issue  
would be "just capable" to implement that  
as a global unified solution for all such use cases.  
In particular not when the contributor cannot test  
all such use cases with reasonable effort.

Simply put:  
I think the root cause of such inconsistencies is  
the "worse is better" style how ReaR develops, cf.  
<https://en.wikipedia.org/wiki/Worse_is_better>  
This style is the only one which works in practice.
