jsmeix commented at 2026-09-02 11:46:¶

A generic problem is that subshells
do not inherit traps of the parent shell
so when a subshell gets a signal as in
https://github.com/rear/rear/pull/3631
that signal will not be reported
by this trap of the ReaR main shell here.

Because bash runs commands within subshells
it means when a command process gets a signal
that signal will not be reported
by this trap of the ReaR main shell here.

This makes it rather questionable
if at least the current implementation of
generic signal reporting by a trap in the main shell
would be sufficiently useful in practice
i.e. that it is worth the risk and effort
and
if perhaps the whole idea of implementing
generic signal reporting does not make sense
and
if perhaps individual signal handling at
each individual place is the only way
which can be done in practice
but
the latter is likely not worth the effort in general
except in specific cases where it is known that
signal handling is actually needed in practice
e.g. as in https://github.com/rear/rear/pull/3631

I make this pull request a "draft" until it is clear
if it makes sense at all to proceed here.

jsmeix commented at 2026-09-04 12:30:¶

@gdha
as far as I currently understand it your enhancement in
https://github.com/rear/rear/pull/3631
is still needed because its initial comment reads (excerpt)

the subshell (or its tar/dd/... children)
is terminated by a signal

See my comment in this pull request here in
https://github.com/rear/rear/pull/3634/changes
which describes my current understanding
of generic signal reporting:

# Signals are an error handling problem because one would have to implement
# additional signal (error) handling everywhere as signals can appear everywhere at any time.
# The actual problem is that there is no generic way to get a message when a signal is raised
# so in particular when a signal terminates ReaR there is no message about the signal
# which makes it almost impossible for the user to find out why ReaR had terminated,
# cf. https://github.com/rear/rear/pull/3631
# A generic issue is that subshells cannot inherit traps of the parent shell
# so when a subshell gets a signal it cannot be reported by a trap in the main shell.
# Because bash runs programs within subshells it means when a program gets a signal
# (as in https://github.com/rear/rear/pull/3631) that signal cannot be caught by a trap
# neither in the main shell nor in a subshell where the program is called.
# Only the program itself could catch and report the signal it got.
# So all we can do is providing a generic signal reporting function
# that can be used as signal handler at other code places as needed and
# register that function here as signal handler for the ReaR main shell
# to notify the user when the ReaR main shell process (MASTER_PID)
# got a signal that would usually terminate ReaR.

On the other hand
the initial comment
https://github.com/rear/rear/pull/3631
also reads

e.g. the whole rear process tree receives SIGTERM from
a timeout, the OOM killer, or a session/scope teardown

When it is the ReaR main shell process (MASTER_PID)
which gets a termination signal, then the
generic signal reporting functionality
in this pull request should report that signal.

As expected there is no message that the subshell got SIGTERM.

But that SIGTERM causes different behaviour because
the default behaviour is to proceed with 'recover'
without manual disk layout configuration.

As far as I understand it this happens because in
usr/share/rear/layout/prepare/default/250_compare_disks.sh
the matching code part is

    input_value="$( UserInput -I DISK_LAYOUT_PROCEED_RECOVERY -t "$timeout" -p "$prompt" -D 'yes' )" && wilful_input="yes" || wilful_input="no"
    if is_true "$input_value" ; then
        is_true "$wilful_input" && LogPrint "User confirmed to proceed with '$WORKFLOW'" || LogPrint "Proceeding with '$WORKFLOW' by default"
    else
        # The user enforced MIGRATION_MODE uses the special 'TRUE' value in upper case letters
        # that is needed to overrule the prepare/default/270_overrule_migration_mode.sh script:
        MIGRATION_MODE='TRUE'
        LogPrint "User enforced manual disk layout configuration"
    fi

so the subshell is $( UserInput ... ) in

input_value="$( UserInput -I DISK_LAYOUT_PROCEED_RECOVERY -t "$timeout" -p "$prompt" -D 'yes' )"

and SIGTERM to that subshell results that input_value is not true.
This is perfectly right because SIGTERM of that UserInput call
makes it fall back to the safest way how to proceed here
which is manual disk layout configuration.

"rear -D recover" without interruption works well

FYI:
I did all the above "rear recover" attempts
within one single booted recovery system.
When one interrupts "rear recover"
after the disk layout was recreated
then one must manually umount all
what is mounted under /mnt/local
before one can run "rear recover" again
(otherwise "rear recover" fails with
"The disk layout recreation had failed"):

RESCUE localhost:~ # umount -a
