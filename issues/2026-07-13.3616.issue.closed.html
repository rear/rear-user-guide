Is your feature request related to a problem? Please describe.¶

2026-07-13 10:07:29.485829852 Creating tar archive '/tmp/rear.tCzbLTGpwQ7rQN2/outputfs/image/backup.tar.gz'
2026-07-13 10:42:20.094543594 ERROR: tar failed with return code 2 and below output:

This means that the archiving process ended prematurely, or did
not even start. As a result it is unlikely you can recover this
system properly. Relax-and-Recover is therefore aborting execution.

==== Stack trace ====

However, we only save the log file when the exit code is 0. It would be better to save always the backup.log file to have at least some output from tar.

Why is this the case? Because we use the Error function. Perhaps, we could before doing the error do a:

cp $v "${TMP_DIR}/${BACKUP_PROG_ARCHIVE}.log" "${opath}/${BACKUP_PROG_ARCHIVE}.log" >&2

jsmeix commented at 2026-07-15 07:49:¶

the public accessible initial part of
https://access.redhat.com/solutions/4524101
shows only the problem but neither solution nor cause
because it is "Subscriber exclusive content"
so I asked Google AI about

Rear backup failing with tar message: value -1 out of time_t range

and it replied:

the error is caused by corrupted file metadata on your system,
specifically an invalid timestamp (value -1) on at least one file.
Because tar cannot handle negative Unix timestamps
(dates before January 1, 1970) under certain configurations,
the rear mkbackup process fails with return code 2.
Here is how you can find the broken files, repair them,
and successfully complete your backup.

Step 1: Find the Corrupted Files
Use the find command to scan your system for files
with a modification time (mtime) that precedes the Unix epoch:

# find / -mtime +$(( `date -u +%s` / 86400 - 1 )) 2>/dev/null
[Use code with caution.]

Alternative:
If the issue is caused by a broken script
or a mounted filesystem that accidentally
set a date far in the future
(causing a 32-bit time_t overflow),
use this command instead:

# find / -newermt "1 day" 2>/dev/null
[Use code with caution.]

Step 2: Repair the Timestamps
Once you identify the affected files,
you can update their timestamps to the current system time
using the touch command.
You can combine the search and fix into a single automated command:

  For files in the "past" (before 1970):

  # find / -mtime +$(( `date -u +%s` / 86400 - 1 )) -exec touch {} + 2>/dev/null
  [Use code with caution.]

  For files in the "future" (overflow/beyond year 2038):

  # find / -newermt "1 day" -exec touch {} + 2>/dev/null
  [Use code with caution.]

Step 3: Run the Backup Again
After updating the invalid timestamps,
restart your ReaR backup process:

# rear -v mkbackup
[Use code with caution.]

Why does this happen?

The Root Cause:
This error typically happens due to incomplete file transfers,
misconfigured NFS mounts, database dumps, or virtual filesystems.
These processes sometimes write a -1 (often an internal error code)
directly into the filesystem metadata as a timestamp.

The ReaR Behavior:
While a standalone tar command might only log a warning
and continue, Relax-and-Recover (ReaR)
treats tar exit statuses strictly.
To guarantee a reliable bare-metal restore
in a disaster recovery scenario, ReaR intentionally
aborts the backup whenever tar encounters a metadata error.

[AI responses may include mistakes.]
